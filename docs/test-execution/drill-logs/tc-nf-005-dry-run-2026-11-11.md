## What this run does and does not show

- 7 audit rows were written to the source after the backup (--simulate-writes).
- The backup was made 0 s before the failure, so the recovery-point figure shows that the mechanism works; it does not show that the daily schedule has been running.
- The dataset holds 3,774 rows (187,329 byte archive). Recovery time grows with data size, so a production-sized dataset needs its own run.
- The data is synthetic (`scripts/synthetic_data.py`); no real student records are involved.
- The recovery point is the age of the newest backup at the simulated failure. It evidences the 24 hour limit only when that backup came from the scheduled daily job.
- Application validation covers `/healthz` and the utilization report. Modules that are still stubs (authentication, equipment, reservations, approvals) are not exercised.
- The case is complete only when it is run on the isolated test deployment with the scheduled backup job, and the register row is updated with a link to that log.
